Raspberry Pi Server Hardening Checklist

Eighteen checks, in the order I'd do them on a fresh Pi. Every one of these runs on the Pi sitting under my desk right now — it hosts thirteen services and is reachable from my phone anywhere in the world. Nothing here is theoretical.

Work top to bottom. The first five matter far more than the rest.

The five that actually matter

1. SSH keys only — kill password login

Password auth is the single biggest exposure on a Pi. Bots find port 22 in minutes.

On your laptop:

ssh-copy-id gareth@raspberrypi.local

Then on the Pi, edit /etc/ssh/sshd_config:

PasswordAuthentication no
PermitRootLogin no

sudo systemctl restart ssh

Test the key login in a second terminal before you close the first one. If you lock yourself out you're plugging in a monitor and keyboard.

2. Do not port-forward. Use a mesh VPN

This is the one that changes everything. The instinct is to forward port 22 or 8080 on the router so you can reach the Pi from outside. Don't. That puts your home network on the public internet where it gets scanned continuously.

Install Tailscale instead:

curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up

Your Pi gets a private address on a mesh only your devices can join. No open ports, no dynamic DNS, no fail2ban arms race. Free for personal use.

Verify nothing is exposed — from your phone on mobile data, try to reach your home IP. Nothing should answer.

3. Firewall: default deny, explicit allows

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp
sudo ufw allow from 100.64.0.0/10 to any port 22 proto tcp
sudo ufw enable

Swap 192.168.1.0/24 for your own LAN range. The 100.64.0.0/10 line is the Tailscale range — it lets you in over the mesh.

Open service ports the same way, scoped to those two ranges. Never ufw allow 8080 on its own; that's open to anything that can route to the box.

sudo ufw status

Every line should name a source range. A rule with no source is a hole.

4. Never let a secret touch git

API keys belong in .env files that git has never seen.

chmod 600 ~/myproject/.env

In .gitignore, before the first commit:

**/.env
**/*.env
*.key
*.pem

Then actually check, because the mistake is usually in a file you forgot about — a setup script, a deploy helper, a README example:

grep -rInE "sk-[A-Za-z0-9]{20}|ghp_|AKIA[0-9A-Z]{16}" --exclude-dir=.git .

I run this on every backup. It has caught a real live API key sitting in a deployment script I'd written months earlier and forgotten. Committing it would have meant rotating the key and scrubbing history. Two seconds of grep, problem gone.

If a secret is already pushed, rotate it first and rewrite history second. Assume it's compromised the moment it lands on a remote.

5. Automatic security updates

sudo apt install unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades

A server you patch manually is a server you stop patching by March.

Accounts and permissions

6. Delete the default user

If a pi user exists, it's a known username on every Pi on earth. Create your own, give it sudo, then remove it.

sudo adduser gareth
sudo usermod -aG sudo gareth
sudo deluser --remove-home pi

7. Run services as a normal user, never root

In your systemd unit:

[Service]
User=gareth
WorkingDirectory=/home/gareth/myapp

If a service is compromised, the blast radius is that user's files — not the machine.

8. Scope passwordless sudo to exactly one command

If something needs to restart services without a password, give it that and nothing else. In /etc/sudoers.d/myapp:

gareth ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart myapp.service

Not NOPASSWD: ALL. Ever. Edit with sudo visudo -f /etc/sudoers.d/myapp so a syntax error can't lock you out of sudo entirely.

9. Check what can actually log in

awk -F: '$3 >= 1000 && $7 !~ /nologin|false/ {print $1}' /etc/passwd

Anything on that list you don't recognise, investigate.

Network surface

10. Know what's listening

sudo ss -tlnp

Read every line. Anything bound to 0.0.0.0 is reachable from your whole LAN. Bind to 127.0.0.1 where you can, and let the firewall cover the rest.

11. Turn off what you don't use

Bluetooth, Avahi, CUPS and the like ship enabled and most servers never touch them.

systemctl list-units --type=service --state=running
sudo systemctl disable --now bluetooth

12. Static IP by DHCP reservation, not by hand

Set the reservation on the router against the Pi's MAC. Hand-configured static IPs survive right up until the router hands the same address to a laptop, and then you spend an evening on it.

13. Check the router itself

Default admin password changed. UPnP off — it lets any device on your LAN punch holes in your firewall without asking. Remote management off.

Data and recovery

14. Backups you have actually restored

An untested backup is a guess.

rsync -a --delete --exclude '.env' --exclude '.venv' ~/myproject/ /mnt/backup/myproject/

Restore one into a temp directory and run it. Put a reminder in the calendar to do that once a quarter.

15. Boot from SSD, not the SD card

SD cards die from write cycles, usually without warning and usually at the worst moment. An NVMe HAT or a USB SSD is more reliable by an order of magnitude.

16. Watch the temperature

vcgencmd measure_temp

Under load it should stay below about 70°C. Past 80°C the Pi throttles and your services get slow in ways that are miserable to diagnose. If you're near the limit, buy the £8 active cooler.

Keep it honest

17. Read the auth log occasionally

sudo journalctl -u ssh --since "24 hours ago" | grep -i "failed\|invalid"

With keys-only and no port forwarding this should be almost empty. If it isn't, something is reachable that you thought wasn't.

18. Write down what's running and why

One text file listing each service, what it does, what it talks to, and what breaks if it stops. In six months you will not remember, and the day you need it will be the day something is broken at 11pm.

The short version

If you only do three things: keys not passwords, Tailscale not port-forwarding, and grep your repos for secrets before you push. Those three remove most of the realistic ways a home server gets owned.
