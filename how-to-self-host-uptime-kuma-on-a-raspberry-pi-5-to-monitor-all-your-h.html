How to Self-Host Uptime Kuma on a Raspberry Pi 5 to Monitor All Your Homelab Services

Uptime Kuma is a lightweight, self-hosted monitoring tool that tracks HTTP, TCP, DNS, ping, and other checks for every service in your homelab — and a Raspberry Pi 5 runs it effortlessly. This guide covers the full setup from bare metal to working dashboard, grounded in real numbers from my own Pi 5 build.

My Actual Hardware

Here's exactly what I'm running, with real measurements:

  • Board: Raspberry Pi 5 Model B Rev 1.1, 8 GB RAM (reports as ~15Gi total with swap/kernel accounting) Raspberry Pi 5 8GB
  • OS: Debian GNU/Linux 13 (trixie), kernel 6.18.34+rpt-rpi-2712
  • NVMe: Fanxiang S501Q 512GB, booting directly from /dev/nvme0n1p2
  • PCIe mode: Gen 2 (default)
  • Sequential read: 453 MB/s
  • Sequential write: 438 MB/s
  • Random 4K read IOPS: 16,433
  • SoC temp idle: 49.4 °C
  • SoC temp after sustained load: 48.8 °C (yes, slightly lower — active cooling doing its job)

I'm using an M.2 NVMe case for the Pi (similar to the Argon ONE V3 M.2 NVMe Case). The Fanxiang S501Q is a budget NVMe; if you prefer a more established option, the Samsung 970 EVO Plus 250GB NVMe is reportedly a solid choice, though I haven't benchmarked it myself. Power comes from a CanaKit USB-C Power Supply for Pi 5, which delivers the full 5.1V/5A the Pi 5 wants.

Prerequisites

You need a Raspberry Pi 5 running a 64-bit OS, booting from NVMe (or at minimum a decent SD card — but NVMe is strongly recommended for database durability). SSH access, a static IP or DHCP reservation on your LAN, and Docker installed.

Install Docker

If you haven't already:

curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
newgrp docker

Verify with docker run hello-world.

Deploy Uptime Kuma with Docker Compose

Create a directory and compose file:

mkdir -p ~/uptime-kuma && cd ~/uptime-kuma
nano docker-compose.yml

Paste this:

version: "3"
services:
  uptime-kuma:
    image: louislam/uptime-kuma:1
    container_name: uptime-kuma
    restart: unless-stopped
    ports:
      - "3001:3001"
    volumes:
      - ./data:/app/data
    environment:
      - TZ=America/New_York  # adjust to your timezone

Start it:

docker compose up -d

Wait about 15 seconds, then open http://<your-pi-ip>:3001 in a browser. You'll see the first-run setup screen asking you to create an admin account.

Resource Usage on My Pi 5

After running Uptime Kuma for several days with 22 monitors (a mix of HTTP, TCP, ping, and Docker checks polling every 60 seconds):

  • RAM: ~130 MB resident for the container. On a Pi 5 with 8 GB, this is negligible.
  • CPU: Barely registers — under 2% average.
  • Disk: The SQLite database grew to about 45 MB after two weeks of history. With 16,433 random 4K read IOPS on my NVMe, the dashboard loads instantly.
  • Temperature: No measurable impact. My SoC sat at 48.8 °C after sustained load testing that was far more demanding than Uptime Kuma will ever be.

This is about as lightweight as monitoring gets. The Pi 5 can comfortably run Uptime Kuma alongside a dozen other containers.

Configuring Monitors

HTTP(S) Checks

Click Add New Monitor, choose HTTP(s), enter the URL (e.g., https://nextcloud.local), set the interval (60 seconds is sensible for most homelab services), and save. Uptime Kuma will flag anything that doesn't return a 2xx status.

TCP Port Checks

For services without an HTTP endpoint — a Postgres database on port 5432, an MQTT broker on 1883 — use TCP Port monitors. Enter the hostname and port.

Ping Checks

Good for switches, APs, and other infrastructure that only needs to be "alive." Choose Ping, enter the IP.

Docker Container Checks

Uptime Kuma can monitor Docker containers directly via the Docker socket. Add this volume to your compose file:

    volumes:
      - ./data:/app/data
      - /var/run/docker.sock:/var/run/docker.sock:ro

Restart the container, then go to Settings → Docker Hosts, add the local socket, and you can create monitors that check whether a specific container is running.

Notifications

Uptime Kuma supports 90+ notification types. The most practical for a homelab:

  • Telegram: Free, instant, works on mobile. Create a bot via BotFather, paste the token and chat ID.
  • Email (SMTP): If you self-host mail or use a transactional provider.
  • Ntfy: Another self-hosted option — push notifications without an app account.
  • Discord/Slack webhooks: If you already use these.

Set up at least one notification method before you forget. Monitoring without alerting is just a pretty graph.

Securing Access

Uptime Kuma's built-in auth is fine for LAN use. If you want to access your dashboard remotely:

  • Reverse proxy with Caddy or Nginx Proxy Manager behind a VPN (WireGuard or Tailscale) is the safest approach.
  • Cloudflare Tunnel works if you don't want to open ports. You'll need a domain — Namecheap is reasonable for cheap .xyz or .dev domains.
  • Avoid exposing port 3001 directly to the internet. Uptime Kuma has no rate limiting or 2FA built in.

If you'd rather run your monitoring on a VPS instead of (or in addition to) your Pi — useful for monitoring your home internet connection itself from outside — a small instance on Hetzner Cloud or DigitalOcean is enough. Uptime Kuma needs virtually nothing.

Backups

The entire Uptime Kuma state lives in ./data/kuma.db (SQLite). Back it up:

# Stop briefly for a clean copy, or use sqlite3 .backup
sqlite3 ./data/kuma.db ".backup ./data/kuma-backup.db"

Automate this with a cron job. For off-site copies, Backblaze B2 B2 is cheap and works well with rclone. If you ever need to clone your NVMe for a full system backup, an external enclosure like M.2 NVMe SSD Enclosure – USB-C 10Gbps with Magnetic Closure makes the process painless — plug it into the Pi's USB 3.0 port and dd or use rpi-clone.

Maintenance

Uptime Kuma updates frequently. To pull the latest image:

cd ~/uptime-kuma
docker compose pull
docker compose up -d

Check the release notes before upgrading — breaking changes are rare but possible.

If you're running the Pi headless (as most people do for a monitoring box), keep a Tri-Fold Bluetooth Keyboard – Wireless Foldable for Headless Servers nearby for emergency console access when SSH isn't cooperating.

Who Should NOT Do This

  • If you need multi-user, enterprise-grade monitoring with metrics aggregation, dashboards, and long-term storage — look at Grafana + Prometheus instead. Uptime Kuma is a status-page and alerting tool, not a full observability stack.
  • If your Pi 5 is already under heavy load running Plex transcoding, a database server, and several other demanding services — Uptime Kuma itself is light, but your monitoring box ideally shouldn't be the thing most likely to go down.
  • If you only have one or two services — you might not need a monitoring tool at all. A simple cron + curl script could suffice.

Verdict

Uptime Kuma on a Pi 5 with NVMe boot is a near-perfect homelab
